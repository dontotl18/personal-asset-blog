앞선 단계에서 Next.js와 테스트·CI, Supabase의 최소 기반을 만들었지만 아직 로그인도 사용자별 데이터 권한도 없었다. 2026년 8월 10일부터 11일까지는 그 빈자리를 채우는 작업이 이어졌다.

개인적으로 사용할 앱이라고 해서 여러 사람이 자유롭게 가입하는 기능은 필요하지 않았다. 하지만 인터넷에 연결된 데이터베이스에 금융 관련 데이터를 저장할 예정이라면 이야기가 달라졌다. 로그인 화면 하나를 만드는 데서 끝나는 것이 아니라 **누가 어떤 데이터에 접근할 수 있는지 데이터베이스 수준에서도 확인할 필요가 있었다.**

> **이번 단계의 중심 기술**
>
> - **Authentication** — Supabase Auth
> - **Authorization** — PostgreSQL / RLS
> - **Database Test** — pgTAP / Supabase CLI
> - **Application** — Next.js
> - **Browser Test** — Playwright

## 한 명을 위한 인증은 공개 가입을 만드는 일이 아니었다

첫 인증 범위는 공개 회원가입 서비스가 아니었다. Supabase 관리 화면에서 허용할 사용자를 직접 만들고, 애플리케이션에는 이메일과 비밀번호 로그인만 제공했다. 공개 가입 호출은 만들지 않았고 서버 전용 allowlist와 로그인한 사용자의 이메일을 정규화해 정확히 비교했다.

이 구조에는 두 겹의 확인이 있었다. Supabase Auth가 입력한 자격정보로 세션을 만들 수 있는지 확인하고, 애플리케이션 서버는 그 세션이 허용된 사용자의 것인지 다시 검사했다. 로그인 실패와 allowlist 거부는 화면에서 같은 일반 오류로 처리해 계정 존재 여부나 허용 목록 정보를 구분해서 보여주지 않았다.

세션 확인도 로그인 버튼을 누르는 순간에만 하지 않았다. 보호 영역에 들어갈 때 사용자를 다시 확인했고, 익명 사용자나 허용되지 않은 사용자는 로그인 화면으로 돌려보냈다. 로그아웃 뒤에는 보호 route의 직접 URL 접근도 다시 차단됐다.

실제 자격정보를 자동 테스트에 넣지는 않았다. 실제 로그인·세션 유지·로그아웃·보호 route 차단은 자격정보를 기록하지 않는 PC와 모바일 수동 절차로 확인했다.

여기까지 만들고 나서도 문서에는 allowlist가 데이터 소유권을 대신하지 않는다고 분명히 남겼다. **로그인에 성공했다는 것과 그 사용자가 DB의 모든 행을 읽어도 된다는 것은 전혀 다른 문제**였기 때문이다.

## Ownership은 사용자와 데이터의 연결 기준이었다

다음 작업은 인증된 사용자와 Profile 행을 연결하는 것이었다. 이때 이해한 Ownership은 거창한 이론이라기보다 “이 데이터가 어느 사용자의 것인지 DB가 구분할 수 있게 하는 것”에 가까웠다.

Profile은 화면을 렌더링할 때 자동 생성하지 않았다. 사용자가 명시적으로 생성하면 서버가 인증 정보에서 소유자를 정했고, 브라우저가 임의의 소유자 값을 보내는 구조는 만들지 않았다. 삭제는 이 단계의 UI와 일반 사용자 권한에서 제외했다.

당시 Profile에는 표시 이름, 기본 통화, 시간대, 언어 설정이 연결됐다. 설정 기능 자체가 글의 중심은 아니었다. 중요한 변화는 인증된 사용자와 그 사용자의 설정을 잇는 기준이 생겼다는 점이었다.

애플리케이션에서 조회 조건에 사용자 식별자를 넣는 것만으로는 충분하지 않았다. 코드 실수나 예상하지 못한 요청 경로가 생겨도 다른 사용자의 행이 노출되지 않도록 DB에도 같은 경계를 두었다.

## RLS로 DB에서 한 번 더 막았다

RLS(Row Level Security)는 PostgreSQL이 각 행에 대해 현재 사용자가 접근할 수 있는 데이터인지 판단하게 하는 기능이다.

> 로그인 사용자 → DB 요청 → RLS → 접근 가능한 행인지 검사

Profile에는 인증된 사용자가 자신의 행만 조회·생성·수정할 수 있는 정책을 추가했다. 정책은 현재 인증 사용자의 ID와 행의 소유자 ID가 같은지 확인했다. 다른 사용자의 행은 조회하거나 수정할 수 없고, 생성할 때 다른 사용자의 소유권을 끼워 넣거나 수정으로 소유자를 바꾸는 것도 허용하지 않았다. 삭제 정책과 일반 사용자 삭제 권한은 열지 않았다.

화면에서 다른 사용자의 데이터를 숨기는 것과 DB에서 접근을 거부하는 것은 다르다. 전자는 현재 UI가 보여주는 범위를 제한하지만, 후자는 요청이 어떤 경로에서 왔든 행에 적용되는 조건이다. 개인용 앱이어도 원격 DB에 금융 관련 데이터를 둘 계획이라면 이 두 번째 경계가 필요하다고 판단했다.

RLS라는 용어는 이름만 알고 넘어갈 수 있는 종류가 아니었다. Codex가 만든 정책과 테스트 결과를 검토하려면 `auth.uid()`가 무엇을 의미하는지, 소유자 조건이 읽기와 쓰기에서 각각 어떻게 적용되는지 이해해야 했다. 프로젝트에서 개념이 등장할 때마다 Notion에 별도로 정리하며 구현을 따라갔다.

## Audit은 원문을 한 번 더 저장하는 로그가 아니었다

같은 migration에는 Profile 변경을 위한 최소 Audit 기준선도 들어갔다. Profile이 바뀌면 DB가 작업 종류와 대상, 작업한 사용자, 발생 시각, 변경된 필드 이름을 기록했다.

여기서 의도적으로 넣지 않은 정보가 더 중요했다. 실제 이메일이나 Profile 필드의 이전·이후 원문을 감사행에 복제하지 않았다. 보안을 강화한다면서 민감한 값을 또 하나의 로그 테이블에 쌓지 않기 위해서였다.

일반 사용자는 자신의 감사행만 읽을 수 있었고 직접 추가·수정·삭제할 수 없었다. 이 시점의 Audit은 Profile 변경만 다룬 기준선이었으며, 이후의 계좌·자산·거래까지 다루는 완성형 시스템은 아니었다.

## 정책이 있다는 것과 실제로 막히는 것은 달랐다

Profile RLS와 Audit을 처음 추가했을 때는 migration의 필수 SQL 구조를 검사하고, 개발 DB의 catalog와 실제 Profile 생성·조회·수정을 확인했다. 하지만 그 결과만으로 익명 사용자와 다른 사용자의 접근이 PostgreSQL에서 정말 거부된다고 말할 수는 없었다.

정적 검사는 정책 문구가 존재하는지 확인할 수 있다. 실제 역할 테스트는 그 정책 아래에서 요청을 실행했을 때 허용과 거부가 기대대로 일어나는지 확인한다. **“정책 SQL이 있다”와 “실제 사용자 역할에서 접근이 차단된다”는 같은 검증이 아니었다.**

8월 11일에는 Supabase CLI를 프로젝트에 고정하고 DB 전용 검증을 추가했다. 로컬 Supabase DB를 빈 상태에서 재구성해 migration을 적용한 뒤, pgTAP으로 실제 PostgreSQL 역할별 접근 경계를 검사했다. 같은 검증은 별도의 CI 작업에서도 실행되도록 했다.

PostgreSQL role은 DB 요청이 어떤 권한 주체로 실행되는지를 나타낸다. 테스트에서는 실제 자격정보 대신 synthetic 사용자 A와 B를 만들고, `anon`과 `authenticated` 역할 및 사용자 claims를 설정해 경계를 재현했다.

대표적으로 다음 경계를 확인했다.

- 익명 사용자는 Profile을 읽거나 변경할 수 없다.
- 사용자는 자신의 Profile만 생성·조회·수정할 수 있고 다른 사용자의 행이나 소유권을 건드릴 수 없다.
- Audit에는 변경 필드만 남으며 일반 사용자는 그 기록을 직접 바꿀 수 없다.

이 단계에서 마련한 52개의 DB 테스트가 모두 통과했다. 개별 case의 수보다 중요한 결과는 **애플리케이션 mock 바깥의 실제 DB 역할에서도 소유권 경계가 유지된다는 근거가 생겼다는 점**이었다.

## 보호 화면도 로그인 이후의 구조로 바뀌었다

권한 기반을 만드는 동안 화면도 보호된 App Shell 구조로 바뀌었다. 실제로 사용할 수 있던 route는 홈과 설정뿐이었고, 앞으로 만들 기능은 링크로 가장하지 않고 `준비 중` 상태로 표시했다. 홈에도 아직 존재하지 않는 총자산이나 수익 같은 가짜 수치를 넣지 않았다.

데스크톱에는 sidebar와 header를, 모바일에는 전체 메뉴와 하단 내비게이션을 두었다. 두 레이아웃은 같은 보호 route와 로그아웃 경계를 공유했다.

이 과정에서는 모바일 전체 메뉴가 작은 viewport 밖으로 밀려 일부가 잘리는 회귀도 발견됐다. 메뉴 배치를 화면 폭 안으로 조정하고 긴 목록이 내부에서 스크롤되도록 수정했다.

자동 검사에는 320px과 360px에서 가로 overflow가 없는지 확인하는 회귀를 추가했다. 실제 PC와 모바일에서도 메뉴와 보호 경계를 다시 확인했다. 인증과 RLS가 글의 중심이지만, 그 경계를 사용자가 실제로 통과하는 화면까지 연결된 시점이기도 했다.

## 한 명이 쓰는 앱에서 어디까지 확인할 것인가

지금 돌아보면 개인 프로젝트치고 인증과 권한 검증의 비중이 꽤 컸다. 여러 사용자 사이의 모든 공격 가능성을 세세하게 다루거나 복잡한 권한 체계를 만드는 일은 현재 범위에 비해 과할 수 있다.

그렇다고 개인용이라는 이유만으로 Login, Ownership, 기본 RLS와 Secret 보호까지 생략할 수는 없다고 봤다. 특히 이 프로젝트는 원격 Supabase에 금융 관련 데이터를 저장하려는 앱이었다. 이 글의 구현은 모든 개인 프로젝트가 따라야 할 기준이 아니라, **이 프로젝트의 데이터 성격과 저장 위치에 맞춰 선택한 경계**였다. 내부 검증의 비중이 실제 기능보다 지나치게 커지지는 않는지도 이후 작업에서 계속 판단해야 했다.

처음부터 Authentication, RLS, PostgreSQL role을 모두 이해하고 설계한 것은 아니었다. 구현을 검토하려면 개념을 알아야 했고, 개념을 이해할수록 로그인 화면과 데이터 권한을 따로 봐야 하는 이유가 보였다. 문서의 정책이 실제 DB 역할 테스트로 이어지는 과정은 그 차이를 가장 분명하게 보여줬다.

인증과 권한의 경계를 만든 뒤에는 비로소 그 안에 실제 도메인 데이터를 담을 차례가 됐다. 다음 글에서는 금융기관과 계좌, 자산을 구분하고 첫 데이터를 입력하기 시작한 과정을 정리할 예정이다.
