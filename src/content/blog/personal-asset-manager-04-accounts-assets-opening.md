앞선 단계에서 로그인과 사용자별 데이터 권한을 만들었다. 이제 그 경계 안에 실제 자산관리 데이터를 담을 차례였다. 2026년 8월 11일부터 12일까지 금융기관과 계좌, 자산을 등록하는 화면을 만들고, 앱을 시작할 때 이미 보유하고 있던 금액과 수량, 기억하고 있는 과거 거래까지 입력할 수 있게 됐다.

처음부터 이 데이터들의 관계를 자연스럽게 이해했던 것은 아니다. 특히 은행 계좌를 떠올리면 “생활비 통장 자체가 자산 아닌가?”라는 생각이 들었다. 구현과 문서를 함께 검토하면서 금융기관, 계좌, 자산이 각각 무엇을 나타내는지 조금씩 구분하게 됐다.

이 단계는 프로젝트가 **기반을 만드는 앱에서 내가 정보를 직접 넣어볼 수 있는 앱으로 바뀌기 시작한 시점**이었다. 동시에 내부 구조를 다지는 일과 사용자가 실제로 보고 싶은 화면 사이의 우선순위를 다시 생각하게 된 시점이기도 했다.

## 금융기관·계좌·자산을 왜 따로 나눴을까

내가 이해한 구분은 비교적 단순했다.

- 금융기관은 어느 금융회사인지를 나타낸다.
- 계좌는 그 금융기관 안의 어떤 계좌인지를 나타낸다.
- 자산은 그 계좌에서 무엇을 보유하는지를 나타낸다.

예를 들어 하나의 증권사 아래에 ISA 계좌가 있고, 그 계좌 안에서 주식과 ETF, 원화를 보유할 수 있다. 반대로 같은 자산을 일반 증권계좌와 ISA에서 동시에 보유할 수도 있다.

은행 계좌만 생각하면 계좌와 자산을 나누는 구조가 다소 어색했다. 통장에 있는 돈과 통장을 하나처럼 느끼기 쉬웠기 때문이다. 하지만 증권계좌까지 같은 방식으로 다루려면 계좌는 자산을 담는 위치이고, 자산은 금액이나 수량을 추적할 대상이라고 구분하는 편이 더 유연했다.

코드에서는 `institutions`, `accounts`, `assets`가 각각 별도의 데이터 종류로 만들어졌다. 이런 데이터 종류를 Entity라고 부르기도 한다. 이 글에서는 **프로젝트에서 관리하는 하나의 데이터 종류** 정도로 이해하면 충분하다.

계좌는 금융기관과 연결되지만 자산 기준정보에는 특정 계좌를 가리키는 값을 두지 않았다. 이 시점에 계좌별 잔액이나 보유수량을 별도 현재값으로 저장하지도 않았다. 실제로 어느 계좌에서 어떤 자산을 얼마나 보유하는지는 이후 원장 기록을 통해 표현하기 위해서였다.

여기에는 사용자별 소유권 경계도 그대로 이어졌다. 금융기관·계좌·자산은 로그인한 사용자의 데이터로 구분됐고, 계좌가 다른 사용자의 금융기관에 연결되는 경우도 DB에서 막았다. 앞 글에서 만든 RLS와 Ownership이 처음으로 실제 금융 기준정보에 적용된 셈이다.

## 계좌번호는 필요한 만큼만 저장했다

계좌 입력 화면에는 계좌 유형, 기준 통화와 선택적인 개설일·폐쇄일이 들어갔다. 하지만 전체 계좌번호는 입력하거나 저장하지 않았다. 화면에서 계좌를 구분하는 데 필요한 끝 4자리만 받고, DB에도 마스킹된 형태만 보존했다.

개인용 앱이라고 해도 가지고 있지 않아도 되는 민감정보까지 모을 이유는 없었다. 전체 계좌번호를 안전하게 암호화하고 복호화하는 문제를 이 단계에서 새로 만들기보다, 식별에 필요한 최소 정보만 저장하는 쪽을 택했다.

이 선택은 화면의 안내에만 머물지 않았다. 애플리케이션 입력 검증과 DB 제약이 모두 정해진 마스킹 형식만 허용했다. 전체 번호가 필요할 수 있는 미래 기능은 별도의 보안·권한 결정을 먼저 거치도록 남겨뒀다.

## 삭제보다 Inactive를 택했다

금융기관과 계좌, 자산 화면에는 물리적인 삭제 대신 비활성화가 들어갔다. Inactive는 데이터를 없앤다는 뜻이 아니라 **과거에는 사용했지만 현재는 사용하지 않는 상태로 남겨두는 것**이다.

금융 데이터는 지금 보이는 목록만 맞으면 끝나지 않는다. 폐쇄한 계좌나 더는 보유하지 않는 자산도 과거 거래에서는 계속 참조될 수 있다. 기준정보를 지워버리면 그 거래가 어느 계좌와 자산에 관한 것이었는지 연결이 끊길 수 있다.

그래서 일반 사용자에게 금융기관·계좌·자산의 DELETE 권한이나 삭제 UI를 열지 않았다. 계좌에는 폐쇄일을 선택적으로 남길 수 있고, 자산은 비활성화한 뒤 같은 데이터로 다시 활성화할 수도 있었다. 기관을 비활성화한다고 연결된 계좌를 연쇄적으로 비활성화하지도 않았다.

처음에는 단순히 목록에서 치우는 기능처럼 보였지만, 실제로는 과거 기록의 식별자를 유지하기 위한 선택이었다. 삭제와 비활성화가 UI 문구만 다른 기능이 아니라는 점을 이때 이해했다.

## 오늘부터 쓴다고 과거 거래를 전부 입력할 필요는 없었다

기관과 계좌, 자산을 등록한 다음에는 앱을 시작하는 시점의 금액과 수량이 필요했다. 앱을 오늘 사용하기 시작했다고 해서 오늘 이전의 모든 입출금과 매수·매도를 처음부터 재현해야 한다면 시작 자체가 너무 어려워진다.

이를 위해 만든 개념이 Opening이었다. Opening은 **앱을 사용하기 시작할 때 이미 가지고 있던 금액이나 수량을 시작 기준으로 등록하는 것**이다. 기준일과 계좌, 자산을 선택하고 금액 또는 수량 가운데 하나를 입력했다.

이 값은 별도의 현재 잔액 칸을 덮어쓰는 방식으로 저장하지 않았다. 제한된 `financial_events`와 `ledger_entries`에 Opening이라는 첫 사실로 기록했다. 입력한 금액이나 수량은 0보다 큰 십진 문자열로 검증했고, 금액은 당시 자산의 통화와 함께 보존했다. 다만 이 글에서는 내부 Event와 Entry 구조보다, 과거 전체를 입력하지 않고도 현재 상태에서 출발할 기준점을 만들었다는 의미가 더 중요하다.

온보딩 화면은 금융기관 → 계좌 → 자산 → 초기값 순서로 이어졌고, 등록된 Opening을 다시 합산해 입력 결과를 확인할 수 있었다. 사용자가 명시적으로 완료하기 전에는 온보딩이 끝난 것으로 처리하지 않았다.

UI의 조회와 정리 기능이 아직 충분하지 않았던 때에는 Supabase SQL Editor에서 저장된 기준정보와 Opening 관련 테이블을 직접 확인하고 테스트 데이터를 정리하기도 했다. 구체적인 SQL 실행 기록과 시각은 저장소에 남아 있지 않아, 여기서는 내가 데이터를 검산한 경험으로만 남긴다.

## 과거 거래는 바로 잔액에 반영하지 않았다

Opening 다음에는 과거 거래를 입력할 필요가 생겼다. 하지만 당시에는 입금, 출금, 이체, 매수, 매도 같은 거래를 원장에 어떤 규칙으로 반영할지 아직 확정하지 않은 상태였다.

입력 기능이 필요하다고 해서 불완전한 규칙으로 잔액부터 바꾸는 것은 위험했다. 그렇다고 기억하고 있는 과거 거래를 나중으로 미루며 잃어버리고 싶지도 않았다. 그 사이에 둔 것이 Historical Transaction Draft였다.

Draft는 **거래 의도와 입력 내용을 보존하지만 아직 확정 계산에는 영향을 주지 않는 임시 데이터**다. 입금, 출금, 이체, 매수, 매도, 기타 가운데 의도를 고르고, 기준 계좌와 발생 시각을 남길 수 있었다. 필요하면 자산, 금액, 수량과 메모도 함께 입력했다.

중요한 점은 Draft를 등록·수정·삭제해도 총자산, 계좌잔액, 보유수량이나 Opening 검산 결과가 바뀌지 않았다는 것이다. 이 단계의 Draft는 입금·출금·이체·매수·매도·기타 중 어떤 의도이든 아직 실제 원장에 반영되는 거래는 아니었다. 계좌와 자산도 확정된 원장 역할이 아니라 과거 거래의 맥락을 보존하기 위한 참조였다.

나중에 Draft를 실제 금융 이벤트로 바꿀 때는 사용자가 내용을 다시 검토하고, 그 시점의 정식 거래 규칙으로 재검증하기로 했다. 자동으로 잔액에 반영하거나 Draft 필드를 무조건 원장으로 옮기지 않는 경계였다.

## 코드가 맞아도 Remote DB가 뒤처질 수 있었다

Draft 기능을 확인하는 과정에서는 코드 버그처럼 보이는 오류도 겪었다. 앱과 Local DB에는 `historical_transaction_drafts`를 사용하는 변경이 들어가 있었지만, Remote Supabase DB에는 해당 migration이 아직 적용되지 않은 상태였다. `/transactions`가 Remote에 없는 테이블을 조회하면서 실패했고, 관련 migration을 적용한 뒤 정상화됐다.

정확한 오류 문구와 발생 시각까지는 당시 기록에 남아 있지 않지만, 앱과 Local DB보다 Remote DB의 schema 적용이 한 단계 뒤처져 있었다는 점은 당시 기록으로 확인할 수 있었다.

이 일을 통해 Migration이 단지 SQL 파일을 쌓는 작업이 아니라는 점이 더 분명해졌다. 코드, Local DB, Remote DB는 적용 시점에 따라 서로 다른 버전일 수 있다. 애플리케이션 코드가 새 테이블을 기대하더라도 Remote schema가 그 지점까지 오지 않았다면 기능은 동작하지 않는다.

상세한 배포 절차보다 이 단계에서 얻은 교훈은 간단했다. **코드 문제처럼 보이는 DB 오류에서는 코드와 Remote schema가 같은 시점을 가리키는지도 확인해야 한다.**

## 내부 기반보다 먼저 보고 싶었던 화면이 있었다

기관과 계좌, 자산, Opening, Draft까지 만들면서 내부 데이터 기반은 점점 단단해졌다. 하지만 사용자의 입장에서는 입력한 내용이 여러 화면에 흩어져 있었다. 내가 처음부터 원했던 것은 금융기관·계좌·자산을 한 화면에서 확인하고, 분포를 차트로 보는 경험에 더 가까웠다.

당시 로드맵은 T1의 다음 작업으로 CSV 가져오기를 두고, 거래원장 이후에 정식 Dashboard를 만드는 순서였다. 8월 12일에는 이 순서를 다시 검토해 CSV 작업을 삭제하지 않고 보류한 뒤 `MVP Dashboard Preview`를 먼저 만들기로 결정했다.

기존 설계를 버린 것은 아니었다. 이미 등록한 Opening 사실과 사용자별 데이터 경계는 그대로 사용했다. 다만 그 기반이 사용자에게 보이는 순서를 앞당겼다. 결정만 남긴 것도 아니었다. 같은 날 `/` 화면에 Opening Dashboard Preview가 실제로 구현됐다.

이 화면은 초기 입력 금액을 통화별로 나누고, 금액으로 평가할 수 없는 수량은 미평가 포지션으로 구분했다. 금융기관·계좌·자산의 관계와 분류별 분포도 보여줬다. 환율이나 시장가격이 없는데 서로 다른 통화를 하나의 총자산으로 합치거나, 현재 자산가치라고 표현하지는 않았다. 화면 제목과 카드에도 `초기 입력 기준`, `초기 입력 금액`이라는 한계를 분명히 표시했다. Draft는 여전히 Dashboard 집계에서 제외했다.

이 우선순위 변경은 내부 기반과 사용자 체감 기능 가운데 하나만 택한 일이 아니었다. 데이터가 말할 수 있는 범위는 지키면서, 지금 가진 데이터로 먼저 확인할 수 있는 화면을 만든 선택에 가까웠다.

## 첫 데이터를 담았고, 이제 실제 거래 규칙이 필요해졌다

이틀 동안 금융기관·계좌·자산을 구분하고, 물리 삭제 대신 비활성화를 적용하고, 전체 계좌번호 대신 최소 식별정보만 저장했다. Opening으로 앱 시작 시점의 기준을 만들고, 과거 거래는 Draft에 안전하게 보존했다. Remote schema가 코드보다 뒤처지면 어떤 문제가 생기는지도 직접 겪었다.

무엇보다 문서에 있던 데이터 모델이 실제 입력 화면과 첫 Dashboard로 이어졌다. 처음부터 계좌와 자산의 차이, Opening과 Draft의 의미를 모두 알고 시작한 것은 아니었다. 구현을 확인하고 데이터를 직접 넣어보는 과정에서 왜 나뉘어 있는지를 이해했다.

Dashboard를 더 빨리 보고 싶다는 요구는 Opening 데이터만으로 제한된 Preview를 앞당겼다. 동시에 Draft를 실제 잔액과 보유수량에 반영하려면 더 이상 임시 구조만으로는 부족했다. 입출금과 이체, 거래를 어떤 금융 사건으로 남기고 원장에 어떻게 기록할지 정해야 했다.

다음 단계에서는 Opening 위주였던 원장을 실제 입출금과 거래까지 확장하게 된다.
