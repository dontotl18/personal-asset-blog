Personal Asset Manager에서 금융 데이터를 기록한다는 것은 계좌의 현재 잔액 칸을 바꾸는 일과 다르다. 앱을 시작하는 기준값은 Opening으로 남기고, 과거 거래를 나중에 검토할 수 있도록 Draft에 보관하며, 확정한 거래는 Financial Event와 Ledger Entry로 기록한다. 이 기록을 검증한 뒤 실제 금융 사실로 확정하는 과정이 Posting이다.

이 글은 복식부기 전체나 투자 거래 규칙을 설명하지 않는다. 현재 프로젝트에 구현된 Opening, 외부 입금·출금, 독립 수수료·세금이라는 범위를 기준으로, 각각의 용어가 무엇을 맡고 어떻게 연결되는지 정리한다.

**현재 잔액은 따로 덮어쓰는 값이 아니라, 게시된 기록을 바탕으로 나중에 계산할 값이다.**

## 먼저 전체 흐름 보기

현재 구조에서는 입력의 성격에 따라 바로 원장에 반영되는지, 잠시 보관되는지가 갈린다.

```text
앱을 쓰기 시작하는 기준값
        ↓
Opening
        ↓
과거 거래를 임시로 보관
        ↓
Historical Transaction Draft
        ↓
확정할 금융 사건을 검증
        ↓
Posting
        ↓
Financial Event ── 1개 이상 ── Ledger Entry
        ↓
기록이 쌓여 만드는 Ledger
```

Opening과 정식 거래는 Event와 Entry 구조로 남는다. 반면 Draft는 이 흐름 앞에 있는 staging 데이터다. 거래처럼 보이는 정보를 담고 있어도 아직 원장 기록이나 잔액의 근거는 아니다.

## Opening — 과거 전체 대신 시작 기준을 남기는 방법

Opening은 단순히 첫 번째 거래가 아니다. 사용자가 앱을 시작하는 기준일에 이미 보유한 금액 또는 수량을 기록하는 **시작 기준값**이다.

예를 들어 몇 년 전부터 사용하던 계좌의 모든 입출금 내역을 처음부터 옮기지 않더라도, 특정 기준일의 금액이나 보유수량을 Opening으로 남기면 그 시점부터의 변화를 이어 기록할 수 있다. 그래서 Opening은 과거 거래를 한 건씩 재현한 결과가 아니라, 기록을 시작하기 위한 별도의 금융 사실이다.

이 프로젝트의 Opening은 계좌와 자산을 참조하고, 금액 또는 수량 가운데 하나만 가진다. 금액이면 당시 자산의 기준 통화를 함께 snapshot으로 저장하고, 수량이면 통화를 두지 않는다. 기준일은 프로필 시간대를 기준으로 미래일이 될 수 없고, 새 Opening에는 활성 상태인 자기 계좌와 자산만 쓸 수 있다.

Opening도 실제로는 Financial Event 한 건과 Ledger Entry 한 건으로 저장된다. 다만 일반 거래와 달리 발생 시각 대신 기준일을 사용하며, 시작값이라는 전용 의미를 가진다.

```text
Opening
  = 기준일에 보유한 금액 또는 수량

Deposit
  = 기준일 이후 실제로 발생한 증가
```

두 기록이 모두 금액을 늘릴 수는 있지만, 뜻과 시간적 위치가 다르다. 이 차이를 남겨야 시작값과 이후 변화를 한데 섞지 않는다.

## Historical Transaction Draft — 확정하지 않은 과거 거래 보관함

Historical Transaction Draft는 과거 거래를 잃지 않기 위한 임시 저장소다. 사용자는 입금, 출금, 이체, 매수, 매도, 기타라는 의도와 발생 시각, 기준 계좌를 남길 수 있고, 필요하면 자산·금액·수량·메모도 함께 보관할 수 있다.

하지만 Draft가 입력됐다고 해서 잔액이나 보유수량이 변하지는 않는다. Draft는 수정하거나 삭제할 수 있으며, 현재 자동으로 Financial Event나 Ledger Entry를 만들지 않는다. 특히 Draft의 금액과 수량은 과거 입력을 보존하는 값이지, 현재 구현에서 정식 거래로 검증된 결과가 아니다.

따라서 Draft를 “미완성 거래”라고만 부르면 부족하다. 현재 프로젝트에서 Draft는 **거래 의도를 편집 가능하게 보관하는 staging 데이터**이고, 정식 거래와는 별도 구조다. Draft를 검토해 지원되는 거래로 명시적으로 승격하는 기능은 후속 범위이며 자동 반영은 구현되지 않았다.

## Financial Event — 무슨 일이 일어났는가

Financial Event는 하나의 금융 사건을 나타내는 기록이다. 외부 입금이 발생했다거나, 독립된 수수료가 발생했다는 사실이 여기에 해당한다. Event는 “무슨 일이 있었는가”를 담고, 실제 변화를 한 줄 한 줄 적는 역할은 Entry에 맡긴다.

현재 정식 거래로 구현된 Event 유형은 네 가지다.

- 외부 입금
- 외부 출금
- 독립 수수료
- 독립 세금

정식 거래에는 실제 발생 시각과 그 시점에 사용한 시간대 snapshot, 선택 메모, 재시도 식별 키가 남는다. Opening은 기준일을 사용하므로 일반 Event의 발생 시각 필드는 비워 둔다.

Event는 아직 모든 금융 의미를 해결하는 만능 분류표가 아니다. 내부이체, 매수·매도, 환전, 취소와 정정은 아직 정식 writer로 구현되지 않았다. Event 구조가 이런 확장을 수용할 수 있는 기반을 마련했다는 사실과, 해당 거래 규칙이 이미 동작한다는 사실은 구분해야 한다.

## Ledger Entry — 그 사건이 만든 변화

Ledger Entry는 Financial Event가 특정 계좌와 자산에 만든 변화를 기록한다. Entry에는 계좌, 자산, 금액 또는 수량, 통화, 그리고 증가인지 감소인지가 들어간다.

이 프로젝트는 금액이나 수량에 음수를 넣는 대신, 항상 양수인 크기(magnitude)와 `increase`·`decrease` 방향(direction)을 나눠 저장한다. 금액과 수량은 동시에 넣을 수 없고 하나만 있어야 한다. 금액 Entry에는 통화 snapshot이 필수이고, 수량 Entry에는 통화가 없다.

```text
Financial Event
  = 무슨 일이 일어났는가

Ledger Entry
  = 그 일이 어느 계좌·자산에 어떤 변화를 만들었는가
```

현재의 외부 입금은 증가 방향 금액 Entry 한 건을 만들고, 외부 출금·수수료·세금은 감소 방향 금액 Entry 한 건을 만든다. 수수료와 세금은 어떤 매수·매도에 연결된 비용이 아니라 각각 독립된 Event다.

한 Event에 여러 Entry를 연결할 수 있는 기반도 있다. 예를 들어 미래의 내부이체는 하나의 Event 아래에서 출금 Entry와 입금 Entry를 함께 기록할 수 있다. 그러나 내부이체 writer는 아직 구현되지 않았다. 다중 Entry가 가능한 구조와 실제 다중 Entry 거래의 지원 여부를 같은 말로 다루지 않는 이유다.

## Posting — 저장 버튼을 누르는 것보다 큰 경계

Posting은 입력을 정해진 거래 규칙으로 검증한 뒤 Financial Event와 Ledger Entry로 확정하는 과정이다. 화면에서 `원장 게시`를 누르는 동작은 이 과정을 시작하지만, Posting 자체는 단순한 버튼 클릭이 아니다.

현재는 거래 유형별 PostgreSQL writer가 입력을 받는다. writer는 사용자의 소유권, 발생 시각, 활성 계좌·자산, 양수 decimal 금액, 통화와 거래 유형별 방향을 검증한 뒤 private posting kernel을 호출한다. 브라우저가 Event 유형이나 Entry 목록, 방향, 통화를 임의로 조합해 기록하지 못하게 한 구조다.

kernel은 Event 한 건과 Entry 한 건 이상을 하나의 DB 작업으로 기록한다. 어느 하나라도 구조나 참조 검증을 통과하지 못하면 앞서 만든 Event와 Entry도 함께 남지 않는다. 즉, 금융 사건만 있고 그 사건의 변화 기록이 없는 중간 상태를 피하는 원자성(atomicity)이 Posting 안에 포함된다.

Draft와 Posting의 차이는 다음처럼 정리할 수 있다.

```text
Draft
  = 편집 가능한 임시 보관, 원장에 미반영

Posting
  = 검증 완료, Event와 Entry 생성, 금융 사실로 확정
```

게시된 원장 행은 직접 수정하거나 삭제하는 경로를 열지 않았다. 취소나 정정은 원본을 덮어쓰는 대신 역분개와 대체 Event를 연결하는 방식으로 설계되어 있지만, 이 세부 기능은 아직 구현되지 않았다.

## Ledger — 별도 테이블 이름이 아니라 기록 체계

이 프로젝트에는 `ledgers`라는 별도 Table이 없다. 여기서 Ledger는 `financial_events`와 `ledger_entries`가 함께 만드는 기록 체계, 즉 금융 사실과 그 변화가 쌓인 원장을 뜻한다.

게시된 Event와 Entry는 잔액과 보유수량의 원본이다. 특정 시점의 금액 또는 수량은 그 시점까지 게시된 증가 기록을 더하고 감소 기록을 빼서 계산할 수 있다. 별도의 현재 잔액 필드를 사람이 직접 수정해 원장과 다른 상태를 만드는 방식은 사용하지 않는다.

```text
시점 t의 금액 또는 수량
= t까지 게시된 Opening의 합
+ t까지 게시된 increase Entry의 합
- t까지 게시된 decrease Entry의 합
```

대시보드 집계나 일별 snapshot은 필요할 때 이 원장을 바탕으로 다시 만들 수 있는 파생 데이터로 본다. 다만 현재 Dashboard는 아직 정식 거래를 집계하지 않는다. Opening만 사용해 `초기 입력 기준`을 보여 주므로, 거래를 게시할 수 있게 된 것과 현재 잔액 Dashboard가 완성된 것은 다른 단계다.

## 과거 기록을 현재도 읽을 수 있게 하는 장치

계좌나 자산을 물리적으로 삭제하기보다 비활성화하는 이유도 원장 구조와 연결된다. 새 거래에는 활성 상태인 계좌와 자산만 쓸 수 있지만, 이미 게시된 Event와 Entry는 해당 기준정보가 나중에 비활성화되어도 계속 조회할 수 있다.

통화도 같은 원칙을 따른다. 금액 Entry는 게시 시점 자산의 기준 통화를 snapshot으로 남긴다. 그래서 자산 기준정보의 통화 표시가 나중에 바뀌더라도 과거 거래가 어떤 통화로 기록됐는지는 바뀌지 않는다. 비활성화와 snapshot은 과거 기록을 현재의 기준정보 변경으로부터 지키는 보조 장치다.

금융값은 폼부터 DB 함수까지 JavaScript `number`로 바꾸지 않고 decimal 문자열로 전달한다. 금액과 수량의 허용 자릿수, 양수 여부, 금액·수량 중 하나만 허용하는 규칙을 DB 경계에서도 확인한다. 이 글에서는 “금융 숫자를 정밀도 손실 없이 전달하기 위한 경계”로만 다루며, JavaScript 부동소수점 표현 자체는 별도 기술 주제로 남긴다.

## Idempotency — 재시도가 거래를 두 번 만들지 않게 하기

정식 거래 요청에는 사용자 범위의 idempotency key가 필요하다. 네트워크 재시도나 중복 동작으로 같은 요청이 다시 도착했을 때, 같은 거래가 원장에 두 번 기록되는 일을 막기 위한 식별 키다.

같은 사용자가 같은 key와 같은 입력으로 요청하면 기존 Event를 돌려준다. 같은 key에 금액·발생 시각·계좌·자산·메모처럼 다른 내용이 들어오면 충돌로 거부한다. 반대로 내용이 우연히 같아도 key가 다르면 별개의 거래다. 금융 사건의 동일성을 내용 비교만으로 추측하지 않는 것이다.

이미 저장된 요청을 다시 확인할 때는 현재 계좌·자산의 활성 상태나 현재 기준 통화가 아니라 저장된 Event와 Entry 사실을 기준으로 비교한다. 그래서 과거 거래에 연결된 계좌·자산이 이후 비활성화되거나 자산 기준 통화가 변경돼도, 같은 요청의 재시도 판단은 과거 기록에 맞춰 유지된다.

## 현재 구현의 경계

현재 구조는 금융 데이터를 무작정 저장하기보다, 어떤 입력이 임시 보관인지와 어떤 입력이 확정 사실인지를 분리한다. Opening은 시작 기준을 만들고, Draft는 과거 의도를 보존하며, Posting은 검증된 입력을 Event와 Entry로 확정한다. Ledger는 이렇게 쌓인 기록에서 잔액과 보유수량을 다시 설명할 수 있게 하는 체계다.

다만 이 구조가 곧 완성된 회계 시스템을 뜻하지는 않는다. 현재 정식 거래는 외부 입금·출금과 독립 수수료·세금 네 종류다. 내부이체, 매수·매도, Draft 승격, 취소·정정, 거래를 반영한 Dashboard와 현재 잔액 집계는 후속 범위다.

Opening과 Historical Transaction Draft를 먼저 도입한 과정은 [개발기 #4](/personal-asset-blog/blog/personal-asset-manager-04-accounts-assets-opening/)에서, 실제 입출금 Posting으로 확장한 과정은 [개발기 #5](/personal-asset-blog/blog/personal-asset-manager-05-financial-transactions-ledger/)에서 확인할 수 있다. 데이터 구조와 변경 이력의 기본 용어는 [개념 정리 #1](/personal-asset-blog/blog/personal-asset-manager-concept-01-database-basics/)에서 다뤘다.
