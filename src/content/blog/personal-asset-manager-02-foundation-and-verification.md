개인 자산관리 웹앱을 직접 만들기로 했지만, 바로 기능 구현부터 시작하지는 않았다. 첫 Codex 실전 프로젝트였기 때문에 AI가 어디까지 작업할지, 그 결과를 어떻게 확인할지를 먼저 정할 필요가 있었다.

지금 돌아보면 2026년 8월 6일은 자산관리 기능을 만든 날이라기보다 **앞으로 어떤 방식으로 개발할지를 정한 날**에 가까웠다. 문서 기준선을 세우고, 최소 애플리케이션과 테스트·CI를 연결한 뒤 Supabase를 도입할 첫 경계까지 마련했다.

> **이번 단계의 개발 환경**
>
> - **Frontend** — Next.js 16.3 / React 19 / TypeScript / Tailwind CSS
> - **Backend · DB** — Supabase / PostgreSQL
> - **Test** — Vitest / React Testing Library / Playwright
> - **Dev · CI** — pnpm / Git / GitHub Actions
> - **AI** — Codex

## 코드보다 먼저 프로젝트의 기준을 적었다

첫 commit에는 애플리케이션 코드가 없었다. 대신 `README`와 제품·데이터·보안·테스트에 관한 문서가 먼저 들어갔다.

문서를 많이 만드는 것 자체가 목적은 아니었다. Codex와 작업할 때 채팅에서 나눈 내용을 계속 기억에 의존하면, 어느 순간 확정된 결정과 아직 검토 중인 아이디어가 섞일 수 있다고 생각했다. 그래서 프로젝트 저장소의 문서를 현재 기준으로 삼고, 작업을 시작할 때마다 다시 확인하는 규칙을 만들었다.

대표적인 문서의 역할은 다음처럼 나눴다.

- `ROADMAP`은 지금 어느 단계에 있고 다음에 어떤 티켓을 진행할지 관리한다.
- `DECISIONS`는 이유와 영향까지 확인된 결정을 남긴다.
- `OPEN_QUESTIONS`는 아직 정하지 않은 문제와 결정해야 할 시점을 보존한다.
- `AGENTS`는 Codex가 작업을 시작하고 범위를 확인하며 완료를 보고하는 절차를 정한다.

확정된 것, 아직 정하지 않은 것, 앞으로 할 일과 안전 기준을 한곳에 섞지 않으려는 구분이었다. 한 번에 하나의 로드맵 티켓을 기본 작업 단위로 삼고, 결정되지 않은 문제가 나오면 Codex가 임의로 확정하지 않도록 했다.

나는 목표와 범위, 승인과 중요한 판단을 맡고 Codex는 정해진 범위에서 문서·코드·테스트를 구현했다. Git은 변경 이력을 남기고 GitHub Actions는 같은 검사를 다시 실행했다. **AI가 모든 것을 알아서 결정하게 두기보다 역할과 확인 지점을 나눈 것**에 가까웠다.

## 큰 계획과 당장 할 일을 분리했다

초기 문서에는 거래원장, 투자, 예·적금, 부채와 대시보드까지 장기 방향이 담겼다. 그렇다고 첫날부터 그 모든 기능을 구현하려고 하지는 않았다.

로드맵은 큰 단계로 나뉘었고, 첫 구현 범위는 프로젝트 기반이었다. 실제로 실행되는 앱과 테스트 환경을 만들고, Supabase를 연결할 최소 경계를 준비하는 정도였다.

중요했던 것은 장기 방향과 지금 구현할 범위를 구분하는 일이었다. 계좌와 자산을 분리하고 거래원장을 잔액의 원본으로 삼는 방향은 정했지만, 실제 거래 기능은 아직 만들지 않았다. 인증과 실제 데이터베이스 검증도 다음 작업으로 남아 있었다.

첫날의 애플리케이션은 프로젝트 진입점만 보여주는 작은 화면이었다. 기능이 없다는 사실을 감추기 위한 가짜 금융 화면이나 샘플 데이터도 넣지 않았다. 무엇이 구현됐고 무엇이 아직 아닌지를 분명히 하는 편을 택했다.

## 최소 애플리케이션을 실제로 실행했다

문서 기준선 다음에는 Next.js App Router, TypeScript, Tailwind CSS와 pnpm을 사용하는 최소 프로젝트를 만들었다. 기술 스택을 문서에 적어두는 것으로 끝내지 않고 실제로 설치하고 실행해 개발 서버와 production build가 동작하는지 확인했다.

설치 결과는 lockfile로 고정했다. `.env.example`에는 비민감 변수의 이름과 설명만 두고, 실제 Supabase 값이나 금융 샘플 데이터는 넣지 않았다. 앞으로 금융정보를 다룰 프로젝트인 만큼, 실행 환경을 만드는 단계부터 비밀정보의 경계를 구분했다.

이 단계에서 만든 것은 자산관리 기능이 아니라 **다음 변경을 올려도 프로젝트가 계속 실행되는지 확인할 수 있는 바닥**이었다.

## 테스트가 0개인 상태를 통과로 보지 않았다

다음 작업은 테스트와 CI 기반이었다. 당시 문서에는 실제 테스트 없이 명령만 성공하는 상태를 없앴다는 완료 기록이 남아 있다. Vitest와 React Testing Library로 메타데이터와 초기 화면을 검사하고, Playwright로 production 환경에서 페이지가 정상적으로 열리는지 확인했다.

테스트 도구를 추가한 뒤에는 구성도 한 번 줄였다. 처음 넣었던 React용 Vite plugin이 당시 테스트에는 필요하지 않다는 것을 확인하고 제거했다. 도구를 많이 두기보다 지금 필요한 최소 구성을 남긴 작은 조정이었다.

포맷, lint, TypeScript, 단위·렌더링 테스트와 production E2E 검사는 로컬의 `verify` 명령 하나로 묶었다. GitHub Actions도 같은 명령을 깨끗한 환경에서 다시 실행했다.

이 구조 덕분에 “내 컴퓨터에서는 됐다”는 확인과 GitHub에서 재현되는 확인을 같은 명령으로 비교할 수 있게 됐다. 아직 금융 계산이나 로그인 시나리오는 없었지만, 적어도 기능이 추가될 때 검사 범위를 넓혀갈 출발점은 생겼다.

> **작업 흐름**
>
> 기준 → 구현 → 로컬 검증 → Git·CI → 다음 작업

첫날부터 이후의 모든 운영 절차가 완성된 것은 아니었다. 원격 데이터베이스 적용과 실제 인증, PostgreSQL 역할별 검증은 아직 하지 않았다. 다만 구현 결과를 다음 단계로 넘기기 전에 무엇을 확인할지는 이때부터 정하기 시작했다.

## Supabase도 한 번에 모두 연결하지 않았다

데이터 저장과 인증에는 Supabase를 사용하기로 했지만 첫 도입 범위는 작게 잡았다. 브라우저와 서버에서 사용할 client와 환경변수 경계를 먼저 나누고, 브라우저 코드에서 secret이나 service-role key를 사용하는 경로는 만들지 않았다.

데이터베이스 쪽에는 `profiles` 구조를 만드는 첫 migration을 추가했다. 나는 원래 Migration을 Oracle에서 PostgreSQL로 옮기는 것처럼 DB 종류를 바꾸는 작업에 가까운 말로 생각했다. 이 프로젝트에서는 **DB 구조의 변경 이력을 SQL 파일로 남겨 같은 상태를 다시 만들 수 있게 하는 방식**이라는 의미로 더 자주 사용됐다.

첫 migration에는 profile의 기본 구조와 RLS 활성화가 들어갔지만, 실제 사용자의 읽기·쓰기 정책은 아직 열지 않았다. 기본 거부 상태에서 시작하고 인증과 소유권 정책은 다음 단계에서 추가하기로 했다.

이때의 테스트는 migration 파일과 주요 SQL 계약을 정적으로 확인하는 수준이었다. 실제 PostgreSQL 실행과 사용자 역할별 권한 검증은 후속 작업으로 남겼고, 원격 개발 Supabase에도 아직 적용하지 않았다. 첫날은 모든 DB 검증을 끝낸 날이 아니라, 이후 안전하게 확장할 출발점을 만든 날이었다.

## 처음부터 다 알고 설계한 것은 아니었다

프로젝트를 진행하면서 익숙하지 않은 개념이 계속 등장했다. Migration뿐 아니라 Local DB와 Remote DB, Ownership, RLS, RPC, Audit 같은 용어는 그때그때 따로 정리했다.

Codex가 만든 결과를 확인하려면 코드가 동작하는지만 보는 것으로는 부족했다. 왜 구현 범위를 나누는지, 왜 데이터베이스 변경을 파일로 남기는지 이해해야 다음 판단을 할 수 있었다.

처음부터 모든 구조를 알고 설계했다기보다, 필요한 개념이 나올 때마다 문서와 구현을 함께 보고 내 방식으로 이해해갔다. 첫날 만든 문서 구조는 Codex에 기준을 전달하는 장치인 동시에 내가 프로젝트를 따라가기 위한 지도 역할도 했다.

## 기반은 도움이 됐고, 동시에 무거워지는 출발점이 됐다

2026년 8월 6일 하루 동안 5개의 커밋을 거치며 문서 기준선, Next.js scaffold, 테스트와 CI, Supabase 최소 기반까지 마련됐다. 아직 로그인도, 계좌 입력도, 자산 대시보드도 없었다.

이 기반은 이후 작업에서 현재 티켓과 완료조건을 확인하고, 같은 검사를 반복하며, 결정과 미결정 사항을 기록하는 데 도움이 됐다. 금융정보를 다루는 프로젝트에서 비밀정보와 데이터 접근 권한을 뒤늦게 붙이지 않도록 방향을 잡는 역할도 했다.

한편 지금 돌아보면 개인 프로젝트치고 내부 검증의 비중이 꽤 커지는 출발점이기도 했다. 이후에는 RLS, 감사로그, RPC 권한과 PostgreSQL 역할 테스트까지 확인 범위가 넓어졌다. 모든 검증의 우선순위가 같은지는 계속 판단해야 하지만, Migration과 기본 RLS, Ownership, 로그인처럼 장기적으로 필요한 기반을 일찍 구분해둔 점은 의미가 있었다.

다음 글에서는 이 기반 위에 한 명을 위한 인증과 데이터 권한을 만들고, 문서에 적어둔 보안 경계를 실제로 확인해간 과정을 정리할 예정이다.
