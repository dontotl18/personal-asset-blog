#4에서는 Opening으로 앱을 쓰기 시작하는 시점의 기준값을 만들었다. 하지만 시작점만으로는 그 뒤에 일어난 변화를 표현할 수 없었다. 대시보드에서 초기 입력 금액을 확인하고 나니, 이제 실제 입금과 출금을 시작값 이후의 변화로 원장에 기록할 수 있어야 했다.

2026년 8월 12일부터 13일까지 Opening에 맞춰져 있던 원장 구조를 일반 금융거래까지 기록할 수 있도록 확장했다. 이 과정에서 Financial Event, Ledger Entry, Posting 같은 용어가 본격적으로 등장했다. 처음부터 이 개념들을 모두 이해하고 설계한 것은 아니다. Opening과 Draft를 먼저 사용해 본 뒤 실제 거래가 필요해졌고, 구현과 문서를 따라가며 각각의 역할을 이해하게 됐다.

실제로 완성된 정식 거래는 **외부 입금, 외부 출금, 독립 수수료, 독립 세금** 네 종류다. 이체와 매수·매도는 아직 Draft 의도 또는 후속 범위다.

## 금융 사건과 원장 기록을 나눠 생각하기 시작했다

내가 이해한 Financial Event는 **무슨 일이 일어났는가를 나타내는 하나의 금융 사건**이다. 입금이 발생했다거나 수수료가 나갔다는 사실이 여기에 해당한다.

Ledger Entry는 그 사건이 특정 계좌와 자산의 금액 또는 수량을 어떻게 바꾸는지 남기는 기록이다. 입금이라면 선택한 계좌·자산의 금액이 증가하고, 출금·수수료·세금이라면 감소한다. 이런 Entry가 계속 쌓인 기록 체계를 Ledger, 즉 원장으로 이해했다. 이 프로젝트에는 별도의 `ledgers` 테이블이 있는 것이 아니라 `financial_events`와 `ledger_entries`가 그 역할을 나눠 맡는다.

Opening도 이 구조 밖에 있던 값은 아니었다. 이미 하나의 Event와 하나의 Entry로 저장되고 있었지만, 당시에는 시작 기준값이라는 제한된 의미만 표현할 수 있었다. 이번 확장에서는 금액이나 수량을 음수로 저장하는 대신 양수 크기와 `increase`·`decrease` 방향을 분리했다. 기존 Opening은 모두 증가 방향을 갖고, 앞으로 하나의 사건에 여러 Entry가 연결될 수 있는 기반도 열었다.

중요한 것은 **하나의 사건과 그 사건이 만든 변화를 구분해 기록하기 시작했다는 점**이었다. 입금 한 건은 “입금이 발생했다”는 Event와 “이 계좌·자산의 금액이 증가했다”는 Entry로 남는다. 이후 한 사건이 여러 변화를 만들 때도 같은 틀을 확장할 수 있지만, 그 거래 규칙까지 완성된 것은 아니다.

## 실제 입출금을 원장에 반영했다

거래 화면에는 정식 거래 영역이 추가됐다. 정식 거래를 검증해 확정하는 동작은 실제 UI에서 `원장 게시`라고 표현했다. 사용자는 거래 유형, 발생 일시, 계좌, 자산, 금액과 선택 메모를 입력한다. 새 거래에는 활성 상태인 자기 계좌와 자산만 사용할 수 있고, 발생 일시는 프로필 시간대로 해석한다.

현재 네 거래는 모두 금액 Entry 한 건을 만든다.

- 입금은 금액을 증가시킨다.
- 출금은 금액을 감소시킨다.
- 수수료와 세금은 각각 독립된 비용 사건으로 금액을 감소시킨다.

수수료와 세금을 출금 메모에 섞지 않고 별도 사건으로 남긴 이유는 나중에도 비용의 성격을 구분할 수 있게 하기 위해서다. 다만 현재 구현은 어떤 매수·매도나 다른 원거래에 수수료·세금을 연결하는 구조가 아니다. 각자 독립된 거래로 확정된다.

금액의 통화도 클라이언트가 임의로 보내지 않는다. DB가 선택한 자산의 게시 시점 기준 통화를 읽어 Entry에 함께 저장한다. 이후 자산 기준정보의 통화가 바뀌더라도 이미 기록된 거래의 통화는 바뀌지 않는다. 새 거래의 자격을 판단할 때는 현재 활성 상태를 보지만, 이미 게시된 과거 사실은 계좌나 자산이 비활성화돼도 그대로 조회할 수 있다.

금융 숫자는 폼에서 DB 함수까지 JavaScript `number`로 바꾸지 않고 십진 문자열로 전달한다. 금액은 0보다 커야 하고 소수점 아래 8자리까지 허용된다. 숫자를 문자열로 다룬다는 점이 처음에는 낯설었지만, 금융 데이터의 정밀도 경계에서 불필요한 손실을 만들지 않기 위한 선택이었다. 자세한 정밀도 문제는 별도 기술 글에서 다룰 만한 주제라 이번 글에서는 이 정도로만 남긴다.

## Draft 저장과 Posting은 달랐다

거래 화면에는 기존 Historical Transaction Draft와 새 정식 거래가 함께 있지만, 둘의 역할은 분명히 다르다.

Draft는 기억하고 있는 과거 거래의 의도와 입력 내용을 보존하는 편집 가능한 임시 데이터다. 입금, 출금, 이체, 매수, 매도 같은 의도를 적을 수 있어도 잔액이나 보유수량에는 영향을 주지 않는다. 반면 Posting은 입력을 정해진 거래 규칙으로 검증한 뒤 실제 Event와 Entry로 확정하는 과정이다. 확정된 거래는 직접 수정하거나 삭제하지 않는다.

이번 구현이 기존 Draft를 자동으로 정식 거래로 바꾼 것은 아니다. Draft 테이블과 정식 거래는 계속 분리돼 있고, 사용자가 새 정식 거래를 별도로 입력한다. 향후에는 Draft를 검토하고 부족한 정보를 보완한 뒤 승격하는 방향이 정해져 있지만, 자동 Posting이나 승격 기능은 아직 구현되지 않았다.

이 경계는 과거 입력을 보존하면서도 불완전한 정보를 성급하게 잔액에 반영하지 않게 해준다. 동시에 이제부터 입력하는 확정 입출금은 Draft가 아니라 실제 원장 사실로 남길 수 있게 됐다.

## 여러 기록을 하나의 DB 작업으로 묶었다

정식 거래 저장은 클라이언트가 Event를 넣고 이어서 Entry를 넣는 여러 INSERT로 구현하지 않았다. 거래 유형별 PostgreSQL RPC가 입력을 다시 검증한 뒤 내부 게시 함수에 전달한다.

공통 게시 함수는 Event 한 건과 하나 이상의 Entry를 하나의 DB 작업으로 만든다. Entry 가운데 하나라도 방향, 금액·수량 구조, 통화 또는 소유권 제약을 통과하지 못하면 Event와 앞서 처리된 Entry까지 모두 취소된다. 금융 사건만 있고 그에 대응하는 원장 기록은 없는 중간 상태를 남기지 않기 위한 경계다.

이 공통 함수는 브라우저에서 직접 호출할 수 없다. 인증된 사용자가 실행할 수 있는 것은 입금·출금·수수료·세금처럼 의미가 고정된 네 writer뿐이다. 사용자 ID, 증가·감소 방향, 통화, 임의 Event 유형과 Entry 목록을 클라이언트가 결정하지 못하게 했다. RPC는 이 프로젝트에서 단순히 DB 함수를 부르는 편의 기능이라기보다, 금융 데이터를 정해진 방식으로만 변경하게 하는 제한된 출입구에 가까웠다.

하나의 Event에 여러 Entry를 붙일 수 있는 기반은 생겼지만, 이번 네 거래는 각각 Entry 한 건만 만든다. 내부이체처럼 출금과 입금을 함께 묶는 다중 Entry 거래는 다음 범위다. 공통 구조가 가능성을 열었다는 사실과 실제 거래 규칙이 구현됐다는 사실을 구분해야 했다.

## 같은 저장 요청이 두 번 처리되지 않게 했다

거래 저장에는 Idempotency, 즉 멱등성 안전장치도 들어갔다. 네트워크 재시도나 중복 동작으로 같은 저장 요청이 다시 도착해도 원장에 같은 거래가 두 건 생기지 않게 하는 장치다.

거래 폼은 저장 요청마다 별도의 식별 키를 만들고, DB에는 사용자별로 같은 키를 중복 저장할 수 없다는 제약이 있다. 같은 키와 같은 입력이 다시 들어오면 기존 Event의 ID를 돌려준다. 반대로 같은 키에 금액이나 다른 입력이 달라지면 별개의 거래로 추측해 처리하지 않고 충돌로 거부한다. 거래 내용이 우연히 같다는 이유만으로 서로 다른 거래를 합치지도 않는다.

재시도 판단은 이미 저장된 Event와 Entry를 기준으로 한다. 테스트에서는 같은 요청이 Event나 Entry를 늘리지 않는지, 같은 키의 다른 입력과 교차 사용자 참조가 거부되는지, 잘못된 값 때문에 실패하면 일부 기록도 남지 않는지를 확인했다. 직접 테이블 쓰기와 내부 게시 함수 접근이 닫혀 있는지도 PostgreSQL 역할로 검증했다.

## 기존 Opening을 깨뜨리지 않고 구조를 확장했다

이번 작업에서 가장 조심스러운 부분은 이미 존재하는 Opening이었다. 새 구조가 필요하다고 기존 시작값을 삭제하고 다시 입력하게 만들 수는 없었다.

호환 마이그레이션은 먼저 기존 Opening 관련 행과 검산 결과를 임시로 보존한 뒤 일반 거래를 담을 수 있도록 원장 구조를 넓혔다. 핵심 조건은 구조가 달라져도 기존 Opening의 ID, 계좌·자산 참조, 금액, 수량과 통화가 그대로 남는 것이었다.

변경 뒤에는 마이그레이션 안에서 이전과 이후 데이터를 양방향으로 비교했다. 기존 ID와 금융값, 참조, Opening 검산 결과나 감사 기록 수가 하나라도 달라지면 적용 자체가 실패하게 했다. 단순히 새 구조가 적용됐는지가 아니라 **이미 기록된 시작값이 같은 금융 사실로 남아 있는지**를 완료조건으로 둔 셈이다.

테스트도 같은 경계를 반복해서 확인했다. 기존 Opening 값과 통화 snapshot, 비활성화 뒤 검산이 유지되는지, 새 방향 값과 사용자별 참조 제약이 맞는지, 일반 거래를 추가해도 Opening과 Draft 및 기존 감사 기록이 바뀌지 않는지를 synthetic 데이터로 검증했다. 새 기능을 추가하면서 사용자가 이미 입력한 시작값을 깨뜨리지 않는 것이 이번 확장의 중요한 문제 해결이었다.

## UI뿐 아니라 실제 저장 구조를 확인했다

이 프로젝트에서는 기능이 생길 때마다 UI 결과만 보고 끝내지 않았다. 거래를 입력한 뒤 DB의 금융 사건과 원장 기록을 직접 조회해 의도한 구조로 저장됐는지 확인하기도 했다. UI에 조회와 정리 기능이 충분하지 않은 개발 단계라 SQL Editor에서 테스트 상태를 관리한 경험도 있었다.

공개 글에는 실제 SQL이나 식별값을 남기지 않지만, 화면의 입금 한 줄이 DB에서 Event 한 건과 증가 Entry 한 건으로 저장된 것을 확인하는 경험은 원장을 이해하는 데 도움이 됐다. Ledger와 Posting이 실제 결과를 설명하는 말로 연결되기 시작했다.

다만 Dashboard는 아직 이 정식 거래를 집계하지 않는다. 현재 자산 대시보드는 여전히 Opening만 사용해 `초기 입력 기준` 금액과 미평가 수량을 보여준다. 거래 화면에서는 정식 거래를 게시하고 최소 내역을 볼 수 있지만, 입출금이 Dashboard 숫자를 움직이는 단계까지 완성된 것은 아니다. 거래를 저장할 수 있게 된 것과 현재 잔액·Dashboard 집계가 완성된 것은 별개의 단계다.

## 여기까지가 현재 상태를 따라잡은 기록이다

프로젝트 시작과 작업 기준, 인증과 권한, 금융기관·계좌·자산, Opening과 Draft, 첫 Dashboard를 거쳐 이제 실제 입출금과 비용을 원장에 기록할 수 있게 됐다.

이번 단계에서 Financial Event는 무슨 일이 일어났는지, Ledger Entry는 그 사건이 어느 계좌·자산에 어떤 변화를 만들었는지, Posting은 검증된 거래를 실제 원장 사실로 확정하는 과정이라는 식으로 이해하게 됐다. 하나의 거래를 원자적으로 저장하고, 같은 요청의 중복을 막고, 기존 Opening을 보존하는 안전장치도 함께 마련했다.

아직 내부이체, 매수·매도, Draft 승격, 취소·정정, 거래를 반영한 Dashboard는 남아 있다. 그래서 이 글은 시리즈의 끝이 아니라, **여기까지가 현재 개발 상태를 따라잡기 위해 정리한 과거 기록**이라는 뜻의 마지막 catch-up이다.

이후부터는 이미 끝난 작업을 소급해 정리하는 대신, 새로운 개발에서 의미 있는 단위가 생길 때 다음 개발기로 이어가려 한다.
